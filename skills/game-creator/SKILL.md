# Game Creator

Работай в папке, выбранной пользователем. Продолжение существующей игры начинай с её документов и `docs/game/state.json`, а не с нового опроса или bootstrap. Сохраняй существующие названия документов и движок. Этот набор — рабочие инструкции агенту; доступ к браузеру, редакторам, генерации и MCP проверяется отдельно.

Сначала определи запрошенный результат. При «только идея/концепт/список MVP» закончи на соответствующих документах; исследуй лишь необходимое для них, не устанавливай стек и не начинай сборку. Полный путь ниже применяется, когда поручено довести игру до MVP. Названия фаз не расширяют поручение.

## Конструктор текущей игры

Когда автор сообщил идею, сохрани её словами автора в проекте и сразу открой конструктор по [references/project-dashboard.md](references/project-dashboard.md). По запросам «покажи конструктор», «где мы остановились» или «проанализируй игру» открой состояние текущей игры в том же чате. Для существующей игры сверь исходники, документы и проверки по этапам; показывай доказательства и следующий шаг. Обсуждение разработки самого набора продолжай в его репозитории.

## Первый разговор

Принимай и одну фразу, и готовый авторский концепт. Сохрани исходную формулировку. После поиска аналогов автор решает, что сохранить или изменить. Основные механики, пиллары и ожидаемый опыт формулирует автор. Помогай структурировать его текст и отмечай открытые решения. Перед планированием реализации запроси подтверждение авторского концепта.

При реальном старте с пустой идеей первый вопрос только один: **«Какая у тебя идея игры? Коротко опиши, что делает игрок и что в этом должно увлекать».** Если идея уже описана, кратко отрази её и не спрашивай снова. Примеры и просьба изменить этот инструмент не являются стартом игры.

Следом выясни только недостающее, по 2–3 коротких вопроса за раунд с рекомендуемыми вариантами: основное действие и результат; для кого и какая сессия; ключевое отличие; ограничения первого результата. Не требуй стандартную анкету целиком. Не начинай писать игру, пока существенно разные трактовки core loop не разрешены. Неизвестную монетизацию можно отложить. Если другой стартовый процесс уже собрал ответы, используй их вместо второго интервью. Используй доступный инструмент вопросов Codex или чат; ожидание ответа не означает согласие, независимую работу можно продолжать.

## Путь к MVP

1. **Идея.** Запиши обещание игроку и 1–2 неизвестных, которые нужно проверить. `idea.md` хранит исходный смысл, а не выдуманный согласованный дизайн.
2. **Исследование.** Подключи `game-market-research`. По умолчанию небольшой обзор реальных аналогов и референсов, достаточный для ближайшего решения. Отдельно: факты с URL/датой, наблюдения, гипотезы. Без сети зафиксируй research pending и работай с предоставленными материалами; не называй аналогов найденными. Большую аналитику углубляй по потребности.
3. **Концепт.** `game-design`: одна ясная петля действий, отличительная гипотеза, игрок, правила успеха/ошибки и исключения из MVP. Покажи пользователю компактный результат для уточнений. Если поручено довести до прототипа, продолжай с явно обозначенными обратимыми предположениями.
4. **Feature Index.** `game-mvp`: короткие F-ID, P0/P1/later, зависимости, критерии приёмки и риск. Один замкнутый игровой цикл важнее списка систем. Конкретные решения о камере/вводе пока можно отметить open.
5. **Платформа прототипа.** После концепта и чернового индекса выясни, где проверяем MVP. Если предпочтение неизвестно, предложи локальный HTML/Web; отдельно уточни **2D или 3D**, устройство/управление и бизнес-модель, только когда они влияют на гипотезу. Steam — канал распространения, Unity — движок; это разные поля. Если платформа уже задана, используй её сразу. Сверь и при необходимости сократи P0 после выбора.
6. **Доска до прототипа.** Покажи 2–3 визуальных направления по [references/reference-board.md](references/reference-board.md): камера, композиция, читаемость и стиль. Уже выбранная картинка может быть единственным направлением. Обычно один раунд; запиши выбор или явное делегирование. Если материалы недоступны, обозначь ограничение и спроси о предварительном продолжении. Явный отказ от доски допустим. Сформулируй краткую карточку: петля, P0/исключения, направление, инструменты по этапам и первая игровая проверка.
7. **Сборка.** Для Web — `game-web-builder`, для Roblox — `game-roblox`, для Unity — `unity-mcp-orchestrator`. Roblox-интерфейсы текущих F-ID подключают `game-roblox-ui`: стиль, спецификация, сборка и проверка Studio. Сначала technical-plan и доступность инструментов, затем играбельная петля, обратная связь, конец раунда и restart. Художник, UI, звук и Blender подключаются при конкретной необходимости.
8. **Проверка.** `game-qa`: реальные действия игрока, результат, сброс, ошибки и подходящие устройства. Затем небольшой тест гипотезы с людьми, если они доступны. Технический smoke test не подтверждает интерес игроков и рыночный спрос.
9. **Решение.** Продолжить, изменить или остановить по наблюдениям. Для переноса — `game-platform-port`; для подготовки продвижения — `game-marketing`; для mobile — `game-mobile`. Не обещай автоматическую конвертацию исходников между движками.

Для запроса автора «сделай простые формы» или «найди ассеты» о 3D-предметах Roblox, Unity или Three.js передай выбор способа в `game-asset-pipeline`: предложи Sand3D, Hunyuan3D и исходный вариант. Запускай `game-3d-props` после явного выбора генератора для текущего заказа.

**Граница быстрого MVP:** одна компактная доска → временные ассеты → замкнутый цикл → плейтест. Массовая графика, риги, речь и глубокое визуальное сходство идут после проверки механики. Когда внешний вид сам является главным риском, сначала проверь одну небольшую пробную сцену. Для существующего прототипа доска и интервью не обязательны задним числом.

Перед работой в Windows прочитай [references/codex-windows.md](references/codex-windows.md), для настройки механики и визуальной проверки — [references/playtest-and-visual-qa.md](references/playtest-and-visual-qa.md).

## Сохранение и подключение ролей

Перед каждой новой фичей оцени, хватит ли текущего контекста на реализацию, проверку и сводку. При достаточном запасе продолжай здесь. При нехватке сначала сохрани summary и передай продолжение в чат **«F-ID — название фичи»** по [правилам контекста и передачи](references/context-handoff.md). Правило действует в ручном режиме и у координатора Робокопа, а также внутри незавершённой фичи на ближайшей проверяемой паузе. Прочитай правила перед первой реализацией и после сжатия. Форк наследует историю, поэтому для освобождения окна требуется сжатие или свежий чат по сводке.

После утверждения концепта, Feature Index и платформы задай вопрос «Как будем выполнять фичи: выбираешь каждую сам или запускаем Робокопа?». Перед первой реализацией обязательно спроси «В какую ветку и какой remote отправлять принятые фичи?» или прочитай явно подтверждённое назначение из конструктора. После каждой принятой фичи обнови её строку Feature Index, сделай один коммит с F-ID и push в выбранную ветку. Сообщи F-ID, SHA и remote/ветку. Пока push требует решения, сохрани SHA и возобнови публикацию без нового коммита. Для ручного режима покажи доступные F-ID, порекомендуй первый по зависимостям и приоритету, дождись выбора. Веди одну фичу до пользовательского ревью. Для автономного режима используй локальный диспетчер Game Factory Kit. Порядок запуска и передачи контекста — [references/robocop.md](references/robocop.md).

Для нового проекта используй шаблоны в [assets/templates](assets/templates). CLI набора может создать их командой `init`; вручную создавай только нужные документы. Существующую систему документации не дублируй. Сохраняй фазу, решения, активный F-ID, факт последней проверки и следующий шаг в state.json. Прочитай [references/roles.md](references/roles.md), когда выбираешь исполнителя. Загружай лишь относящиеся к текущему этапу навыки, обычно 1–3 за шаг. Независимые исследование/ассеты/проверку можно делегировать доступным агентам с отдельными файлами; решения своди в один актуальный план.

Фазы: `idea → research → concept → scope → build → playtest → decide → port`. Это ориентир, а не запрет возврата: новые сведения могут потребовать уточнения концепта. `pending`/`not_run`/`unknown` сохраняй честно. Не ставь `pass` на основании чтения кода.
