# Перенос игры

Зафиксируй исходный работающий build, целевую платформу, причину переноса и критерии паритета. Сохраняй исходную папку и документы; не переписывай проверенный прототип на месте без необходимости. Цель может быть один vertical slice, а не вся будущая production-игра.

Составь mapping: правила/формулы/контент/локализация, ассеты и лицензии, input/camera/UI, physics/timing, save/network, услуги площадки. Концепт, F-ID, сценарии и часть данных переиспользуются; JS/C#/Luau lifecycle, физика, UI и сервисы обычно требуют отдельной реализации. Изменение движка само по себе не улучшает игру.

Подключи целевой профиль: Unity через доступный Editor/MCP, Roblox через `game-roblox`, mobile через `game-mobile`, Web через `game-web-builder`. Проверь версии и возможности до обещания сборки. Сделай один end-to-end сценарий и сравни поведение по исходным acceptance: action timing, collision, результат и reset. Разницу, принятую ради целевой платформы, отрази как решение, а не скрытый баг.

Ассеты прогоняй через реальный importer, проверяй units/axes/pivot/materials/rig/clips/collision и права целевого владельца. Performance измеряй заново. Steam рассматривай как канал дистрибуции с отдельными задачами SDK/store/build, а не как движок.

Сохрани port plan, сделанные F-ID, проверки, различия и блокеры. Если поставлена только задача оценки, верни оценку и следующий проверяемый шаг; не создавай второй production-проект автоматически.
