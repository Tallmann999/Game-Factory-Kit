# Исследование источников и инструментов

Проверено 26 октября 2026 года. Это оценка пригодности для переносимого набора, а не рейтинг популярности. Внешние зависимости ниже не установлены автоматически. Цены, условия API и версии следует проверять перед подключением.

## Вывод для набора

Главное недостающее звено — воспроизводимое исследование перед разработкой: вопрос → источники → сравнительная таблица → проверяемая гипотеза → маленький прототип. Ещё один общий «эксперт по геймдеву» этого не заменяет. Нужны отдельные роли исследования рынка и референсов, концепта, ограничения MVP и оценки плейтеста; технические и художественные специалисты подключаются по конкретной задаче.

Бесплатного базового режима достаточно для первых проверок: публичные страницы игр, трейлеры, отзывы, собственные наблюдения и локальный HTML-прототип. Платные базы подключать тогда, когда конкретное решение требует их данных, а не как обязательную часть установки.

### Что в ней полезно

В [гайде о концепте и core loop](https://github.com/dim-s/indie-gamedev-knowledge-base/blob/5e410f4ce7732f3b74f95a2cb60f54e4943a0404/Guides/GameDesign/core-loop-and-concept.md) полезна постановка задачи через опыт игрока и согласованность игрового обещания с повторяющимся действием. Для нашего конвейера это вопросы интервью и проверка концепта: что делает игрок, зачем возвращается и что именно должно подтвердиться на плейтесте. Подключать этот материал при подготовке или пересмотре концепта.

В [OGD](https://github.com/dim-s/indie-gamedev-knowledge-base/blob/5e410f4ce7732f3b74f95a2cb60f54e4943a0404/OGD/OGD.md) есть подробный авторский словарь, сценарии диагностики и границы применения; [история изменений](https://github.com/dim-s/indie-gamedev-knowledge-base/blob/5e410f4ce7732f3b74f95a2cb60f54e4943a0404/OGD/CHANGELOG.md) показывает пересмотр выводов по наблюдениям. Практическая польза — дополнительная линза для мотивации игрока, ритма, прогрессии и расхождения ожиданий с игрой. Наличие ссылок на психологические исследования не подтверждает автоматически каждое конкретное предписание методологии: это мои оценочные выводы по структуре материалов, а не заявление автора о проведённой независимой валидации.

### Что не переносить без адаптации

В репозитории уже есть [готовый `ogd-methodology` v0.9.6](https://github.com/dim-s/indie-gamedev-knowledge-base/blob/5e410f4ce7732f3b74f95a2cb60f54e4943a0404/OGD/ogd-methodology/SKILL.md). Его описание требует применять метод при любых обсуждениях дизайна и маркетинга. Для универсального набора такой триггер слишком широк: он будет конкурировать с ведущим сценарием и другими дизайнерами. Внутри встречается порог медианной сессии в 30 минут; переносить его на короткие Web-прототипы или Mobile как общее правило нельзя. Метрики следует выбирать под жанр, канал и проверяемую гипотезу.

Решение: оставить OGD дополнительным источником и включать по явному выбору или конкретному дизайн-вопросу. Не превращать термины автора в обязательный язык всех проектов. Не переносить установщик, изменяющий обнаруженные копии и использующий симлинки, в основной установочный процесс набора. Для переносимости лучше обычные файлы, фиксированный снимок и явное обновление.

### Важное изменение Steam API

Актуальная документация `IUserReviewsService` прямо отмечает старый `store.steampowered.com/appreviews/<appid>?json=1` как deprecated. Новый метод: `https://api.steampowered.com/IUserReviewsService/GetAppReviews/v1/`, параметры через `input_json`; сортировки и типы отзывов теперь enum, `languages` — список, отсутствует старый `success`. Не копировать старые скрипты из статей без проверки. [Официальная миграция](https://partner.steamgames.com/doc/webapi/IUserReviewsService#Migrating%20from%20/appreviews).

## Как проводить исследование без ложной уверенности

1. Записать идею в 1–3 предложениях, основной глагол игрока и ожидаемое ощущение. Уточнить только то, что изменит поиск.
2. Пока конечная платформа не выбрана, рассматривать рынки как альтернативы. Не использовать Steam-продажи для обоснования Web-рекламы или Roblox-экономики.
3. Собрать короткую таблицу аналогов: ссылка, платформа, дата релиза/обновления, core loop, аудитория-гипотеза, цена/модель, видимые сигналы, отличие нашей идеи. Пометить, что наблюдали сами, что взяли у сервиса, что предположили.
4. Отделить три типа референсов: механика, визуальный стиль, интерфейс. Один хит редко подходит сразу для всех трёх.
5. После доступного просмотра и небольшой выборки отзывов сформулировать 2–3 гипотезы и наиболее дешёвую проверку. Не объявлять нишу свободной по отсутствию результатов одного поиска.
6. В MVP проверять одну главную неопределённость. У заранее выбранной метрики указать, для какой игры она нужна; универсального порога хорошего retention, CTR или длительности сессии нет.
7. После плейтеста обновить концепт и индекс фичей. Дальнейшая платформенная реализация переносит дизайн, контент с подходящими правами и результаты наблюдений; код переносится только при реальной совместимости.

## Что не добавлять в установку по умолчанию

Не нужны всеобщие автопубликаторы, подписки на аналитику, игровые SDK монетизации, произвольные MCP-серверы, удалённые shell-установщики и десятки одинаковых «экспертов». Их наличие увеличивает обслуживание и не улучшает первую игровую гипотезу. Достаточно реестра опциональных подключений с назначением, источником, лицензией, способом проверки и условиями включения.

Художнику, 3D-моделлеру, аниматору и UI-дизайнеру нужны конкретные брифы и проверка результата в игре. Маркетологу нужны сопоставимые данные и проверяемое обещание. Программисту нужен ограниченный MVP и критерии готовности. Именно эти связи между ролями стоит автоматизировать в ведущем скилле.
